What the app is

CleanSheet cleans a messy CSV inside the browser and explains every change. It has two halves: a cleaning engine (plain JavaScript that works on data and returns a list of changes, removals and flags, each with a reason) and a screen that shows those lists and lets a person undo, restore or correct things. Nothing is uploaded or stored.

One action, followed through

Action: press Run cleaning on the sample file.

Reference route (3 stops)

Written as a reference route from the finished code. It has not been walked through interactively.

1. The click: app.js, search $('runPlan').addEventListener

Calls CS.run(state.headers, state.rows, state.plan), resets the user's decisions, then calls renderReview().

2. The work: engine.js, function run

Makes a copy of the rows, applies each switched-on step (trim, names, email, phone, dates, numbers, duplicates, missing), and records a reason for each change. The original rows are never edited, which is why every change can be undone.

3. The result: engine.js function finalize, then app.js function renderReview

finalize takes the engine's lists plus the user's decisions (undone changes, restored rows, typed fixes) and returns the final rows and the change report. renderReview turns that into the counters, tabs and preview you see.

To change this, start here

  • Add a cleaning rule: engine.js, in run add a block like the others, and add its card in interpret.
  • Change which words trigger a rule: engine.js, function interpret.
  • Change wording or layout on the review screen: app.js, functions changesPanel, removedPanel, flagsPanel.
  • Change colors or fonts: the :root block at the top of style.css.
  • Change the sample data: sample-orders.csv, then regenerate sample.js.

A practice to reuse

Write what "done" looks like as something you can observe, then check it by running it.

In this project the scope said the demo should show a compelling cleaning in under a minute. Running the browser test showed the first sentence cleaned only 1 cell, which made a weak demo. That led to the revision recorded in devpost/checklist.md under Revisions (a longer sentence that cleans 21 cells). The same habit works on any project: state the visible result you expect, run it, and let the gap tell you what to change.
